# TechRadar LLM and Tooling Upgrade Plan

Status: proposed; implementation has not started. Date: 2026-09-17.

Background and sources: [upgrade review](2026-09-17-review.md).

## Intended Outcome

Publish reliable, grounded English/Russian digests using a configurable, evaluated model. Preserve the dashboard and extension data contract. Establish a repeatable build before updating framework dependencies.

Default planning assumptions: continue with Anthropic first; retain daily static generation; evaluate Sonnet 5 against Haiku 4.5; add another provider only if evaluation demonstrates a benefit. A database, agent framework, vector search, and hosting migration are not needed for this scope.

## Phase 1 — Establish the Baseline

- [ ] Install a selected, pinned Bun release and run `bun install --frozen-lockfile`.
- [ ] Record test, lint, type-check, formatting, and production-build results. Separate pre-existing failures from upgrade regressions.
- [ ] Add direct `eslint` and `typescript-eslint` dependencies compatible with the existing config.
- [ ] Add a dedicated Vitest configuration that isolates offline unit tests from live parser diagnostics; expose diagnostics through a separate script.
- [ ] Add a PR workflow with frozen install, tests, lint, type-check, build, and artifact checks. Use read-only permissions for verification jobs.
- [ ] Fix the `.ouptut` typo in the clean script and verify which output directories both build modes actually create.

Files: `package.json`, `bun.lock`, proposed `vitest.config.ts`, `.github/workflows/verify.yml`, and test organization.

Exit gate: repeatable offline unit tests and builds, with no undocumented baseline failures. No LLM calls are needed for this phase.

## Phase 2 — Protect Feed Publication

- [ ] Extract an importable generation function from `scripts/generate-feed/index.ts`; keep CLI execution behind a main guard.
- [ ] Validate source items individually, deduplicate URLs, and add fetch deadlines and source-health reporting.
- [ ] Build and validate candidate artifacts in a staging directory. Publish them only after all checks pass; commit all three together. A sequence of file renames is not a transaction, so retain backups/recovery for local publication and stage the complete set in CI before committing.
- [ ] Proposed initial gate: at least one healthy nonempty source and valid summaries for at least 80% of selected unique posts, with an absolute minimum of one. An empty source run preserves old data and exits unsuccessfully. Adjust this threshold after observing source reliability.
- [ ] Validate existing history before extending it; do not replace corrupted history with an implicit empty baseline.
- [ ] Test all-source failure, all-model failure, partial success, malformed dates, invalid history, interrupted publication, and repeat execution on the same date.

Exit gate: failed generation leaves the last good artifacts intact, returns a failure status, and cannot produce a successful empty digest commit.

## Phase 3 — Make Model Calls Configurable and Validated

Files: `scripts/generate-feed/summarize.ts`, `index.ts`, `.env.example`, workflow, and summarization tests. Add a small typed provider module if needed.

- [ ] Introduce proposed settings `DIGEST_MODEL`, `DIGEST_MAX_POSTS`, and `DIGEST_MAX_OUTPUT_TOKENS`; validate values at startup. Initially default to the current Haiku model.
- [ ] Replace `any` request/response boundaries with SDK types and a narrow summarizer interface returning validated data plus model/usage/status metadata.
- [ ] Use Anthropic structured output with an SDK-compatible schema. Keep local checks for category, valid URLs/dates, exactly three takeaways per language, length limits, and required prefixes.
- [ ] Treat article text as untrusted source material, explicitly disallow following embedded instructions, and require claims to be supported by the provided text. Do not give summarization tools or secret-bearing context.
- [ ] Define handling for refusal, output truncation, timeouts, invalid credentials/model IDs, rate limits, and malformed responses. Bound transient retries; fail fast on configuration errors.
- [ ] Cache successful summaries using source/content/model/prompt/schema identity. Persist cache across CI runs, and invalidate it on model or prompt changes.
- [ ] Record usage and elapsed time without logging credentials. Enforce a configurable run budget using conservative pre-call estimates and actual post-call usage.

Exit gate: mocked provider tests cover the failure matrix, cached repeats avoid duplicate calls, and existing digest consumers work unchanged. Native structured output still requires local validation and factual evaluation.

## Phase 4 — Evaluate and Select the New Model

Prepare 30 saved public-source fixtures spanning short/long posts, sparse RSS excerpts, mixed languages, misleading marketing claims, and embedded instruction attacks. Store expected facts and source references alongside inputs. Use the same content and output contract for every candidate.

1. Compare `claude-haiku-4-5-20251001` with `claude-sonnet-5` using access verified in the actual API account.
2. Set a bounded token budget and explicitly verify candidate-specific thinking/output settings rather than copying defaults. Test truncation at the current 1,024-token cap before raising it.
3. Record schema compliance, unsupported claims, preserved key facts, natural Russian, duplicate takeaways, latency, tokens, and total cost.
4. Have a bilingual reviewer score outputs blind. Suggested promotion gates: 100% final schema compliance, zero material unsupported claims in the fixture set, average quality at least 4/5, and quality no worse than baseline. These are proposed acceptance criteria, not measured outcomes.
5. Set a numeric per-run spending ceiling before paid evaluation. Select the least costly candidate that meets the agreed quality criteria; include retries in the comparison.

Optional comparison: add OpenAI Luna/Terra only after a typed Responses API adapter and provider-contract tests exist. Keep provider-specific authentication, structured-output mapping, status handling, and usage accounting separate. Astra is a quality reference if needed, not the assumed daily default. For Astra, current documentation excludes `none` reasoning and several sampling parameters; consult the [migration guidance](https://developers.openai.com/api/docs/guides/latest-model) before constructing requests.

Exit gate: commit a dated evaluation report with inputs, model IDs, settings, prompt/schema versions, rubric, costs, and selected default. Never claim improvement from a model name alone.

## Phase 5 — Roll Out and Observe

- [ ] Run the candidate into a separate output directory for three scheduled generations. Compare source coverage, digest quality, cost, and errors with the baseline.
- [ ] Switch `DIGEST_MODEL` only after evaluation gates pass; verify web/extension rendering in EN and RU.
- [ ] Add visible generation time and stale-data handling wherever digest data is displayed.
- [ ] Extend the secret scanner and its tests if a provider is added; current regex matching is only a partial safeguard. Never put API keys in `VITE_*` variables or extension assets.
- [ ] Observe seven daily runs. Alert on failed jobs, stale output, excessive skips, or spending above the chosen limit.

Rollback: restore the previous model/configuration and last known good complete artifact set. Use the previous model's cache identity. If that model becomes unavailable, preserve the last good feed and surface staleness until an evaluated replacement is ready.

## Phase 6 — Upgrade the Toolchain Separately

1. Resolve current stable versions and peer/engine requirements from package registries and official release notes. Record exact selected versions and the resolved lockfile diff.
2. Update React/React DOM together and compatible TanStack Start/router packages in an isolated change. Verify generated routes, server functions, SSR, hydration, and the Bun production server.
3. Migrate the Vite alias to a supported stable Vite 8 release with compatible React plugin and Vitest. Check the existing Nitro v2 integration and `FOR_SITES=true` output path before choosing a replacement; preserve the deployment adapter until its successor is tested.
4. Update remaining libraries in small groups. Run dependency vulnerability checks and assess reachable issues; do not blindly apply major-version fixes.
5. Pin CI runtime versions and introduce grouped dependency-update PRs with required checks.

Verification commands after each relevant change:

```bash
bun install --frozen-lockfile
bun run test
bun run lint
bun run format:check
bun run build
bun run build:node
bun run check:secrets
```

`build:node` currently omits explicit type-checking; retain a separate type-check gate. Smoke-test the actual deployed build mode, extension ZIP download, public routes, and Chrome new-tab loading. Roll back tooling changes by restoring the matching manifest, lockfile, and configuration together.

## Optional Product Follow-Up

Decide whether “AI Insight” should remain deterministic analytics with a clearer label, or consume an additional daily generated insight artifact with source references. Treat genuine LLM insights as a separate feature with its own schema, factuality tests, stale state, and cost budget. Keep trend scores deterministic and explainable.

## Decisions to Finalize Before Implementation

- Maximum daily generation and one-time evaluation spend.
- Whether Anthropic-only delivery is sufficient or a second provider is required.
- Which production target must be supported: Bun, Node/Nitro, or both.
- Who reviews Russian-language quality and approves the evaluation rubric.

The default path is Phases 1–5 with Anthropic, then Phase 6 as independent tooling PRs. These decisions do not block the baseline and publication-reliability work.
